# Minimal Radioberry TX-only C++ kernel driver for Raspberry Pi 5

This directory is a learning implementation of the shortest practical path
from a C++ program's bit string to the Radioberry FPGA:

```text
fixed C++ string -> write() -> /dev/radioberry-tx -> C++ kernel core
                 -> 32-bit words -> RP1 PIO FIFO -> GPIO 5/4 -> FPGA
```

It is an actual Linux kernel module. The module is not a userspace GPIO
bit-banger and the example is not a CLI. The data-path decisions are written
in freestanding C++17; a small C translation unit supplies the Linux and RP1
interfaces that are not C++ APIs.

## Read this limitation first

The input is a string representation of the **literal serial bits delivered to
the Radioberry TX interface**. It is not a text message, packet encoder, BPSK
modulator or arbitrary-data radio protocol. With the normal Radioberry
gateware, each 32-bit wire word is consumed as the existing TX I/Q word format.
Consequently, `"101"` means the word `0xa0000000`, not the RF transmission of
three information bits using an automatically selected modulation.

Producing a useful RF signal requires all three of these layers:

1. Generate correctly scaled, timed and packed I/Q sample words for the desired
   modulation.
2. Configure the Radioberry radio through its six-byte SPI control protocol,
   including the correct TX state, frequency and drive settings.
3. Send those I/Q words through this driver's `write()` path.

This module implements item 3 and exposes a raw ioctl for item 2. It does not
invent undocumented control values. Transmission can radiate RF, so connect a
dummy load or suitable attenuated test setup and comply with local regulations.

## Why C++ needs a C shim

Linux does not provide a supported C++ kernel programming environment. Kernel
headers are C, kernel build rules assume C, and there is no `libstdc++` in the
kernel. A wholesale conversion of Linux-facing code would add ABI and build
risk without teaching anything about the TX algorithm.

This module therefore has a strict boundary:

| File | Language | Responsibility |
| --- | --- | --- |
| `tx_core.cpp` | freestanding C++17 | validate bits, pack words, retry FIFO, own TX setup order |
| `bridge.h` | C ABI | declarations shared across the language boundary |
| `linux_shim.c` | kernel C | SPI driver, `/dev` operations, user copies, mutex, RP1 calls |
| `tx_ioctl.h` | C ABI | stable six-byte raw SPI-control ioctl |
| `radioberry-tx.dts` | DTS | bind SPI0 CS0 and enable RP1 PIO |
| `examples/send_fixed_bits.cpp` | userspace C++17 | fixed bit string and a `write()` loop, no CLI |
| `tests/tx_core_test.cpp` | host C++17 | fake hardware tests of the exact C++ core |

`tx_core.cpp` includes no Linux header and no standard-library header. It uses
no allocation, exception, RTTI, virtual function, constructor or destructor.
Its exported entry points use `extern "C"`, so `linux_shim.c` can link them by
stable symbol name.

## Exact bit packing

The driver accepts only ASCII byte values `0` and `1`. It validates a complete
write before touching the PIO FIFO. It then takes groups of at most 32 input
characters and builds an unsigned 32-bit word from left to right.

| Input to one group | FIFO word | Bits clocked to FPGA |
| --- | --- | --- |
| `"1"` | `0x80000000` | `1` followed by 31 zero padding bits |
| `"101"` | `0xa0000000` | `101` followed by 29 zero padding bits |
| 32 ones | `0xffffffff` | 32 ones |
| 33 ones | `0xffffffff`, `0x80000000` | 33 ones followed by 31 padding zeros |

Padding is unavoidable because the inherited FPGA interface transfers a full
32-bit word. If padding must not be interpreted as samples, the caller must
provide complete 32-bit units or define framing at a higher layer.

The return value is the number of original ASCII bit characters accepted. It
does not count FIFO words or padding. If an RP1 error occurs after earlier words
were queued, `write()` returns a short positive count because queued words
cannot be rolled back.

## Hardware path on Raspberry Pi 5

Raspberry Pi 5 routes this interface through the RP1 PIO service, not the older
BCM GPIO peripheral assumptions used by earlier Pis. The module opens an RP1
PIO client, claims any free state machine and installs the original nine-word
Radioberry TX PIO program at instruction address zero.

| GPIO | Direction | Meaning |
| --- | --- | --- |
| 4 | Pi to FPGA | serial clock, generated by PIO side-set |
| 5 | Pi to FPGA | serial data, one MSB-first bit per PIO `OUT` |
| 12 | FPGA to Pi | ready handshake, pulled down by the Pi |

The PIO state machine first polls GPIO 12. Once READY is high, `PULL BLOCK`
takes one 32-bit word from the TX FIFO. `SET X,31` and the `OUT/JMP` loop clock
all 32 bits. It then returns to the ready handshake for the next word.

The program is loaded at fixed origin zero because its jumps are absolute. If
instructions 0 through 8 are already occupied, module probing fails instead of
silently running incorrectly. Closing the RP1 client releases the claimed state
machine and program.

### Why there is no DMA

The production driver uses DMA and 16 KiB buffers for sustained I/Q streaming.
This learning driver writes directly to the four-word PIO TX FIFO through RP1
RPC calls. That removes kfifos, DMA buffers, callbacks, work queues and the
minimum 16 KiB accumulation rule. It is appropriate for short experiments and
understanding the path. It is not an efficient continuous high-rate SDR stream.

If the FIFO is full, the core sleeps for approximately 1 to 2 ms and retries,
up to 1000 times per word. A pending signal interrupts this wait. This is a
simple bounded policy, not a hardware completion guarantee.

## File-operation behaviour

`/dev/radioberry-tx` is created with mode `0600` and permits one open file at a
time. `write()` accepts 1 to 4096 characters. A zero-length write succeeds;
invalid characters or an oversized write return `EINVAL`.

Closing the file does not stop the PIO state machine and does not prove that the
FPGA has consumed every queued word. The module keeps the state machine alive
until its SPI device is removed or the module is unloaded. A successful write
means the data was queued into the PIO path, not that RF emission finished.

The mutex serialises open state, writes, SPI control and device removal. User
memory is copied before the lock is acquired, then the C++ core receives only a
kernel buffer. This is important because dereferencing a userspace pointer in
C++ kernel logic would be unsafe.

## Raw SPI control ioctl

`RB_TX_CONTROL` exchanges exactly six bytes with the Radioberry control SPI
device in mode 3. The request buffer is replaced by the six response bytes.
It is intentionally raw because the meanings and valid combinations belong to
the selected gateware/control protocol.

```cpp
#include "tx_ioctl.h"
#include <sys/ioctl.h>

rb_tx_control control{{/* six protocol bytes */}};
if (::ioctl(fd, RB_TX_CONTROL, &control) < 0) {
    // errno describes the copy, device or SPI failure.
}
```

Do not copy placeholder bytes into a live transmitter. Derive them from the
gateware version and existing Radioberry control implementation.

## Prerequisites

- A 64-bit Raspberry Pi 5 kernel and matching kernel build headers.
- The external Raspberry Pi RP1 PIO driver and matching `pio_rp1.h`.
- Its `Module.symvers`, because this module calls symbols exported there.
- `g++` for the same AArch64 target as the kernel.
- `dtc` for the overlay and a C++ compiler for the example/tests.
- Correct Radioberry gateware already loaded into the FPGA.

The original repository expects the RP1 driver from the Raspberry Pi kernel
work used by this project. External-module symbol versions and headers must
come from the same build. Mixing revisions may compile and still be ABI-unsafe.

## Build

Run on the Pi from this directory:

```sh
make \
  KERNEL_HEADERS=/lib/modules/$(uname -r)/build \
  RP1_SYMVERS=/home/pi/git/rp1-driver/Module.symvers
```

If `pio_rp1.h` is outside the kernel include tree, pass the directory which
contains its `linux/` subdirectory:

```sh
make RP1_HEADERS=/path/to/include \
     RP1_SYMVERS=/path/to/rp1-driver/Module.symvers
```

The custom Kbuild rule compiles only `tx_core.cpp` with freestanding flags. It
uses `$(CROSS_COMPILE)g++` by default, or `RB_CXX=/path/to/compiler`. This is an
experimental out-of-tree GCC integration. Kernel CFI, LTO, shadow-call-stack,
BTI/PAC and compiler-version policies can require extra flags or make this
approach unsuitable. Validate the resulting module against the exact target
kernel rather than assuming that a host build proves compatibility.

## Load gateware, overlay and module

Gateware loading remains separate. The repository's loader is under
`SBC/rpi-5/utility/gatewareloader`:

```sh
make loadFPGA
# Put the correct radioberry.rbf in that directory.
sudo ./loadFPGA
```

Install `radioberry-tx.dtbo` into `/boot/firmware/overlays/`, add this line to
`/boot/firmware/config.txt`, then reboot:

```text
dtoverlay=radioberry-tx
```

Load the RP1 PIO dependency first, then this module:

```sh
sudo insmod radioberry_tx.ko
ls -l /dev/radioberry-tx
dmesg | tail
```

Do not enable the repository's full `radioberry` overlay/module at the same
time. Both implementations compete for SPI0 CS0, GPIOs, PIO instructions and a
state machine.

## Send the fixed example

Edit `kBits` in `examples/send_fixed_bits.cpp`, then:

```sh
make example
sudo ./examples/send_fixed_bits
```

There are no command-line options. The program opens the device, repeats
`write()` if the kernel returns a short count, closes it and reports how many
input bits were queued.

## Tests and what they prove

```sh
make test
```

The host test links the exact `tx_core.cpp` against fake bridge functions. It
checks MSB alignment, tail padding, a 33-bit boundary, validation before output,
FIFO backpressure, cleanup and rejection after stop. `nm` also rejects obvious
C++ runtime or allocation dependencies.

The test does not compile `linux_shim.c`, load a module, exercise RP1 firmware,
verify GPIO timing, configure RF or validate real FPGA consumption. Those must
be tested on the target Pi 5 with appropriate measurement equipment.

## Suggested learning order

1. Read `examples/send_fixed_bits.cpp` to see the system-call boundary.
2. Read `rb_file_write()` in `linux_shim.c` to see safe user copying and locking.
3. Read `Transmitter::write()` in `tx_core.cpp` to follow validation and packing.
4. Read `rb_hw_try_put()` to see the RP1 FIFO transaction.
5. Read the nine PIO instructions and trace READY, PULL and the 32-bit loop.
6. Read `rb_probe()` and `Transmitter::start()` to understand ownership setup.
7. Read both cleanup paths in reverse order and check every acquired resource.

## Deliberate omissions

There is no RX, DMA, poll/select, mmap, sample-rate API, frequency conversion,
modulator, packet framing, buffering thread, CLI, automatic gateware load or
boot-time installer. Each omission keeps the minimum TX path visible. The next
engineering step for continuous I/Q is DMA with explicit buffer ownership and
completion semantics, not simply increasing `RB_MAX_BITS`.
